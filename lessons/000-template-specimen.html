Template specimen — not a curriculum lesson

The shape of a lesson

This document exercises the course's lesson template and its shared stylesheet. It teaches nothing about Airflow or dbt, because a real lesson belongs to the curriculum and not to the template. A template nobody has used is not a template.

A lesson in this course is a short read and then a substantial exercise — never both in the same sitting. This specimen is the read. Its exercise is the authoring of the next lesson, and it is specified below rather than demonstrated.

Why a specimen rather than a lesson

The curriculum for this course is a continuous project: one synthetic orders API, one warehouse, one dbt project, one DAG that grows lesson by lesson until it holds up in production. That sequence is owned by the curriculum, and a first lesson that taught something invented to fill this page would put a lie in the repository and a false anchor for every lesson that would link here later.

So this file is labelled as what it is, and it does one job: it proves that the template's markup and the assets/lesson.css stylesheet produce a readable, printable lesson. Every component a lesson can use appears here at least once, which is the only way to know the stylesheet covers all of them. The live version of this page is the README-shaped future lesson's job, not this file's.

On the file name. This is lesson 000 and is not part of the sequence: the first real lesson takes 01. The zero is a slot for a document that demonstrates the format, so that no curriculum lesson has to be demoted to that role.

The read

Three things about a lesson are worth knowing before writing one, and none of them are Airflow.

The read and the exercise are separate sittings. The read is short enough to finish in one pass; the exercise is substantial enough that doing it immediately would mean doing it badly. That split is the constraint from MISSION.md — study in substantial blocks — and it is why the anatomy puts a hard boundary between the explanation and the specification. It is also why the short-lesson constraint is pedagogical rather than cosmetic: it forces the source material to be decomposed, and the decomposition is most of the value.

The exercise is a specification. It states a requirement, names the interface surface, and lists the constraints — then it stops. The learner writes the code. There is deliberately no worked implementation inside an exercise, and none adjacent to one: a worked example that sits next to the exercise is a transcription target, and transcription produces the feeling of understanding instead of its structure. The argument is recorded in ADR 0007 and is not reopened here.

A lesson points at files; it does not contain them. Every reference to code in this course is an anchor to the live file in the repository. The reason is ordinary: a copy inside a lesson is a copy that goes stale, and a reader who trusts a stale copy writes against code that no longer exists. The component for it is .live-file, and this lesson uses it twice:

Live file: <repo>/AGENTS.md § Lesson anatomy (required)

When the course's project exists, the same component points at a pipeline module. That path is written in the specimen rather than linked, because the repository root is not built yet and a link to nothing teaches nothing:

Reserved, not linked yet: <repo>/dags/pipeline/<module>.py

The anatomy, all six parts

The six required elements, with the component that implements each and a link to the place in this document where it appears. The same six are required of every lesson, and they are the reason this file is longer than its content strictly needs: the specimen exists to prove the slots work.

1. The specification-shaped exercise — .exercise
Requirement, interface surface, constraints. On this page.
2. The worked example, placed elsewhere — .worked-ref
A pointer to a file that holds one, in a different directory from the exercise. On this page.
3. The statement of what was just built — .built
One declarative sentence about the artifact the exercise produced. On this page.
4. The primary source cited — .source
An entry from RESOURCES.md, read at the version pinned there. On this page.
5. The primary source recommended next — .next-source
One entry, one anchor, and a reason. On this page.
6. The follow-up question — .followup
A question with more than one defensible answer, asked before the reader moves on. On this page.

The rule behind the list is that a reader can tell which slot they are looking at without being told, because each one looks different. That is the stylesheet's whole job: one accent, spent on the exercise and nowhere else, and everything else carrying its weight with rules, weight and whitespace instead of colour.

On the accent. One warm signal-orange per page, and it marks the exercise only. It is not Airflow's teal: a course that borrows the tool's colour reads as official documentation, and this course is meant to read as one person's working repository.

Committed motion

A lesson may embed a rendered clip by relative path. The clip and the composition that produced it are committed together, and the media-freshness seam fails if the two ever drift apart — which is the only thing in the repository that would notice. This is the one subject ADR 0002 admits Remotion for: a hand-off between processes, where the ordering is hard to hold in prose and trivial to watch.

Worked example

The worked example for this exercise is the lesson template, and it is deliberately not in this file. Live file: <repo>/assets/lesson-template.html

Exercise

Requirement

Write the next lesson in this course — a short read and a substantial exercise, on a subject taken from the curriculum sequence — and get it past the constraints below. Write the lesson; this page does not contain it.

Input
The curriculum's own sequencing: the subject the next lesson is supposed to own, whatever that is. Not supplied here, because inventing one is how a specimen turns into a lie.
Output
One file at lessons/NN-<slug>.html, carrying all six anatomy elements, openable by double-click with no build step and no running toolchain.
Interface surface
The stylesheet's classes, which are the whole API of a lesson: .masthead, .eyebrow, .standfirst, .lede, .sidenote, .live-file, .exercise, .spec-label, .spec-list, .worked-ref, .built, .source, .next-source, .followup, .crosslinks, .endmatter, .skip-link. Plus ../assets/lesson.css as the only stylesheet, and ../assets/lesson-template.html as the only worked example.
Constraints
  • No sans face in any font stack — in the lesson or in anything it adds to the repository.
  • One accent on the page, spent on .exercise. A second hue is a failure, not a feature.
  • Every claim traced to an entry in RESOURCES.md, cited at the version pinned there.
  • Code referenced as a live file, never pasted. Cross-links to sibling lessons carry an anchor.
  • The lesson's own exercise is a specification: requirement, surface, constraints, and no code.
  • Readable and printable: a printed copy must keep its exercise, and the file must survive both colour schemes with the text still legible.
How you know it passes

Print it. If the exercise is not on the paper, the lesson is not done — that is the cheapest check in the whole format and the one most often skipped. Then open it with the network off, which is the condition it will actually be read under.

# Open the lesson. Windows, no toolchain, no server:
start "" "lessons\01-<slug>.html"

# Open the lesson. macOS or Linux:
xdg-open lessons/01-<slug>.html   # or: open lessons/01-<slug>.html
What was just built

One shared stylesheet carrying the course's visual identity, one lesson template carrying the anatomy, and this specimen proving both render — a lesson format that can be opened offline, read in either colour scheme, and printed with its exercise intact.

Primary source

The claim that a lesson must open without a running toolchain follows from where the toolchain lives: the project is the Astro CLI project at the repository root, and a lesson is a document that precedes it. The pinned Airflow version this course reads at is recorded in the supported-versions page; this specimen asserts no version-specific fact, which is why it cites it rather than a claim built on it.

Read next

Before authoring the first real lesson, read the Astro CLI repository README to the point where you can say what astro dev parse checks and what it does not. The first lesson will ask you to verify something with it, and a specification that asks for a verification the reader cannot yet name is not a specification.

Before you move on

This page spends its one accent on the exercise and leaves the read entirely uncoloured. Argue for one change to that allocation that would make a reader more likely to finish the exercise — then name which anatomy element your change puts at risk, and what you would have to give up to pay for it.
