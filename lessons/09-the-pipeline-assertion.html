Nightly — lesson 09

The pipeline assertion

After this lesson you have one command that proves the nightly pipeline produces the right numbers, and you know why the hardest part of writing it is not the pipeline.

Everything up to here has been a pipeline that runs. It parses, it schedules, it extracts, dbt builds four models, and a table of daily KPIs appears in the warehouse. Every one of those numbers is currently a claim the course is making about itself and has not checked once.

The read

The hard part is the expectation, not the check. Comparing a table to a table is easy. What is worth doing is the comparison, and that means deciding what the right numbers are — which is the same problem the dbt models already solved. The obvious move is to ask the models: build the same query twice, or read the values out of a staging model and compare. Do not do that. An expectation produced by the thing under test cannot fail for a reason that matters. It fails when a column is renamed, or when a schema moves, and it stays silent on the day someone changes a business rule and gets the same wrong answer twice.

So the expectation is a second implementation of the same rules in a different language. The pipeline states "an order that is cancelled or returned did not produce revenue" once, in SQL, in int_orders_enriched.sql. The assertion states it again in Python, over HTTP, from the orders API, and adds up integers. Two statements of one rule is the price of an independent answer, and the disagreement between them is not noise — it is the entire value of the exercise. It is also the moment the argument becomes real: if the two disagree about which orders count as revenue, one of them has misread the rule, and you have learned something about the rule that neither implementation could have taught you alone.

On the page size. The assertion walks the API's pagination at 500 rows per page; the pipeline asks for 1000. That is not a rounding difference. If both clients paged the same way over the same boundaries, a shared misunderstanding of the envelope would cancel out and both would agree on the wrong answer. Different boundaries, same rows, is the check.

Why twice. One pass proves a number. Two passes over the same window prove something stronger and much rarer: that the pipeline is a function of its inputs rather than of its history. An extraction that appends instead of upserting produces the right table the first time and twice as many rows the second. A model that accumulates instead of replacing does the same. Airflow's own guidance is that a task's re-run must produce the same outcome, and that the way to get there is to replace INSERT with UPSERT — so the second run is not an extra nicety, it is the property the framework is asking you for.

What the assertion is allowed to look at. Only the warehouse, and Airflow's report of the run it triggered. It does not import a pipeline module and it does not search a source file for a string, because either one lets the pipeline be renamed into passing: assert that a model is called fct_daily_order_kpis or that a file contains counts_as_net_sale, and the assertion survives the day someone fixes a bug by renaming a column while going green on the day someone breaks a number. A whole-pipeline assertion that reads internals is a test of the author's memory.

Two of the pipeline's claims are genuinely not visible in its output, and for those the assertion reads Airflow's state. The first is that Cosmos rendered every dbt model into a task: a model missing from the graph still leaves a correct table if an earlier run built it. The second is that the run read the window it was asked for — read from the task's own returned value, because two runs of the same window have different logical dates and that difference has to be shown not to matter.

The Airflow 3 thing. schedule="@daily" does not mean what it looks like. It resolves to CronTriggerTimetable, whose data interval is a single instant — the run labelled 2026-10-01 has the interval [2026-10-01, 2026-10-01) — so a pipeline that extracts the day that just ended raises on every scheduled run and reads nothing. Manually triggered runs pass, because they take their window from configuration instead. This project declares CronDataIntervalTimetable in dags/pipeline/intervals.py; the measurements are in the environment baseline, and the reasoning is why that file exists.

What comes out the other end is one command, from the repository root, that is also the onboarding gate — it checks that the stack is up, that Cosmos imports where DAGs are parsed, that dbt is executable where tasks run, that the data source resolves by service name, that there is exactly one pipeline and it parses — and then does the one thing the course exists to be able to do.

What comes next is not a second assertion. This is the primary seam, and every module after this one extends it rather than adding to it: a new model joins the list of models Cosmos must have rendered, a new column joins the list of columns compared, and the existing command's output changes because the pipeline now does more. The test for any proposed new check is whether breaking it would leave the pipeline wrong in a way a reader would care about. If the only consequence is that a test would fail, it belongs at one of the other three seams.

Worked example

The worked example for this exercise is the assertion itself, and it is deliberately not in this page. Open tests/assert_pipeline_kpis.py and read it in this order: the module docstring, which says what the file is for and why the expectation is not SQL; then expected_daily_kpis(), which is the second implementation; then compare(), which is the whole comparison. What to look for in it is what is not there — no select against a staging model, no import from dags.pipeline, no assertion on the text of a file. A reader stuck on the exercise can open that file and see a completed version of the same ideas; a reader working through the exercise cannot transcribe a line out of this page, because the implementation is in the repository and not here.

Exercise

Requirement

Extend the one command so that it proves a backfill composes: the same window, extracted as two adjacent halves in two separate runs, must leave the warehouse in exactly the state one whole-window run leaves it in.

Input
The pipeline and the assertion as they stand. A window of [2026-02-01T00:00:00Z, 2026-06-15T00:00:00Z) holding 1116 orders over 134 days, and a source with orders on both sides of it.
Output
One command, unchanged in name and location, whose output states whether the halves composed. It remains a single command from the repository root and prints the evidence — the counts, and which days differed if any did.
Interface surface
The functions already in tests/assert_pipeline_kpis.py: expected_daily_kpis(), trigger_and_wait(), read_fact_table(), read_raw_counts(), compare(), digest(), and the Airflow REST client (api_get, api_request). Add whatever else the proof needs, but keep the run-configuration contract: both bounds always travel together in the run conf.
Constraints
  • Still one command. Do not create a second assertion file, and do not add a second entry point — the whole point of the seam is that there is one thing to run.
  • The two halves must be adjacent and non-empty, and the split point must fall on a day the source generates orders for, so that the boundary is exercised rather than skipped.
  • Each half's run must be able to see the other half's effect. Any preparation that resets the warehouse between the two runs defeats the exercise, and the assertion must not do it silently — a step that discards state is a step a reader has to be told about.
  • State equality, not digest equality. Compare what the warehouse holds, so that a difference is reported as a difference in days and rows rather than as two opaque strings.
  • The expectation stays independent. The two halves are checked against values computed from the source, not against the whole-window run's output, or the comparison would be circular.
  • The DAG is not yours to change. No edit to dags/pipeline/ or to the dbt project may be needed, and if one turns out to be needed, that is a finding about the exercise, not an invitation to make it.
  • Externally observable only, as before: no reading a DAG file, no importing a pipeline module, no searching a file for a string.
How you know it passes

Three runs of the one command, and three things to read off the output. All three must hold, and the first two must already hold today — if they do not, something upstream of this exercise is wrong and worth finding first.

# 1. The command still passes end to end, and is still deterministic:
.venv/Scripts/python tests/assert_pipeline_kpis.py   # exits 0

# 2. Re-run it. The expected, first-run, second-run and halves digest
#    are all the same string, and the command takes no flags and no
#    arguments to make that true.

# 3. Break the composability on purpose and watch it fail for the
#    right reason: make the extraction append instead of upsert, or
#    give one model a filter that quietly drops a day, and confirm the
#    output names the day and the column. Then put it back.
What was just built

One command that runs the nightly pipeline twice over a known window and proves the daily KPIs in the warehouse are correct — computed from the source rather than from the models — and unchanged by the second run, on top of the staging, intermediate and mart layers it checks and the extraction window that feeds them.

Primary source

The claim that this is a test worth writing, and the claim that a re-run must produce the same outcome, both come from the Airflow best practices doc, read at the pinned version 3.3.2. Under Testing a Dag it says DAGs should be treated as production-level code with tests "to ensure that they produce expected results", and it separates the layers this course keeps separate: unit tests that call an operator directly, and dag.test(), which is "an integration test" needing a metadata database and "not a substitute for the unit tests above". Under Creating a task it gives the reason for running twice — a task re-run must produce the same outcome, so "do not use INSERT during a task re-run… Replace it with UPSERT" — and it names data_interval_start as the partition to read and write, which is the window this course extracts.

Read next

Read the dbt best practices, and start with How we structure our dbt projects and Idempotence in dbt — both are sections of that index. The second is the closest thing in the vendor documentation to this lesson's subject and it was not written for a course exercise; the first answers the question the exercise raises. Stating one business rule twice, in two languages, forces the question of where each statement belongs: which layer is allowed to decide what a cancelled order means, and which layer is only allowed to add up what that layer decided. That is the stg → int → fct split, and it is the reason this project has three schemas rather than one.

Before you move on

The assertion proves the mart is right over 134 days, twice, and proves nothing at all about the other 46 days the source contains, nor about any day that arrives late tomorrow. Argue for one change to the window or the expectation that would widen what this command can say — then name what it would cost, and whether the cost lands on the assertion or on the pipeline. If your answer is "it would only slow the command down", you have not thought about it yet.
